# План интеграции Chronos

> **Архивный документ.** 2026-07-27 принято решение перейти на Gadgetbridge и
> открытый протокол Tseho Link. Прикладная интеграция Chronos не продолжается.
> Подтверждённый BLE/NUS bring-up сохраняется как диагностический baseline.
> Актуальный план: [`GADGETBRIDGE_INTEGRATION_PLAN.md`](GADGETBRIDGE_INTEGRATION_PLAN.md).

Дата: 2026-07-27
Статус: план реализации после успешного BLE/NUS bring-up

## 1. Цель

Использовать Chronos как телефонный transport adapter для часов:

```text
Chronos app
    ↕ BLE Nordic UART Service
Chronos framing/parser
    ↓ normalized events and state
Watch model
    ↓
Universal UI / built-in skins
```

Chronos не должен становиться частью GUI или основной моделью данных. Его
пакеты преобразуются в ограниченные типизированные структуры часов. Благодаря
этому позже можно добавить другой companion app или transport без переделки
экранов.

Первый полезный релиз должен поддерживать:

- синхронизацию даты и времени;
- состояние соединения и батарею телефона;
- уведомления и входящий звонок;
- текущую погоду;
- управление музыкой и поиск телефона;
- reconnect и повторную синхронизацию.

Навигация является следующим приоритетом после устойчивого первого релиза.

## 2. Подтверждённая отправная точка

На nRF52840 QIAA-C0 уже проверены:

- advertising с именем `Tseho Watch`;
- соединение Chronos с часами;
- Nordic UART Service RX/TX;
- GATT discovery;
- подписка телефона на TX;
- запрос синхронизации `AB 00 03 FE 23 80`;
- получение пакетов от реального Chronos;
- стабильная работа без WDT и повторных reset.

Текущий код принимает отдельные BLE writes, считает байты и сохраняет только
четыре начальных байта последнего пакета. Сборки кадра, декодирования и
прикладной модели пока нет.

## 3. Границы первой реализации

### Входит

- пакеты Chronos, начинающиеся с поддерживаемых сигнатур `0xAB`/`0xEA`;
- сборка кадра из нескольких BLE writes;
- фиксированные буферы без heap и Arduino `String`;
- явные пределы длины строк и коллекций;
- time, notifications, calls, weather, phone battery и controls;
- диагностические счётчики и host fixtures;
- безопасное поведение при неизвестных и повреждённых пакетах.

### Не входит

- загрузка циферблатов Chronos;
- передача медицинских показателей без подтверждённых датчиков;
- полный телефонный справочник;
- хранение истории здоровья;
- OTA через Chronos;
- подмена Universal UI форматом Chronos.

## 4. Целевая структура кода

```text
include/watch/
  chronos_frame.h       framing API and limits
  chronos_protocol.h    decoded packet types
  chronos_model.h       bounded phone-side state

src/protocol/
  chronos_frame.c       BLE chunk → complete frame
  chronos_protocol.c    frame → typed event

src/app/
  chronos_model.c       apply event to normalized state
  chronos_adapter.c     clock/UI/control integration

src/platform/
  ble_softdevice.c      advertising, GATT, RX/TX only

tests/chronos/
  fixtures/             captured and synthetic packets
  test_frame.c
  test_protocol.c
  test_model.c
```

`ble_softdevice.c` не должен знать формат времени, погоды или уведомлений.
Parser не должен вызывать GUI. UI читает только snapshot нормализованной
модели.

## 5. Этапы реализации

### Этап 0 — зафиксировать протокол и реальные fixtures

Работы:

1. Добавить диагностический кольцевой буфер сырых RX chunks.
2. Записать полную начальную сессию Chronos:
   - connect и sync;
   - изменение 12/24-hour setting;
   - одно уведомление;
   - входящий и завершённый звонок;
   - обновление погоды;
   - изменение батареи телефона;
   - команды музыки и find phone;
   - начало/остановка навигации.
3. Сопоставить кадры с текущей официальной реализацией ChronosESP32.
4. Сохранить обезличенные бинарные fixtures и их ожидаемый смысл.

Критерий готовности:

- каждый целевой тип имеет хотя бы один реальный fixture;
- личные тексты, номера и координаты заменены синтетическими значениями;
- неизвестные байты помечены, а не угаданы.

### Этап 1 — надёжная сборка кадров

Работы:

1. Реализовать state machine сборщика:
   - поиск допустимого начала;
   - чтение заявленной длины;
   - накопление нескольких BLE chunks;
   - выдача только полного кадра;
   - сброс по timeout;
   - resync после мусора.
2. Ограничить кадр 512 байтами.
3. Добавить результаты `COMPLETE`, `NEED_MORE`, `REJECTED`, `OVERFLOW`.
4. Добавить счётчики accepted/rejected/overflow/timeout.
5. Проверить разбиение каждого fixture во всех возможных местах.

Критерий готовности:

- один кадр корректно собирается при любом BLE chunking;
- два кадра в одном входном потоке разделяются;
- повреждённая длина не вызывает запись за границы;
- parser восстанавливается после мусора.

### Этап 2 — decoder и нормализованные события

Работы:

1. Ввести tagged union `watch_chronos_event_t`.
2. Реализовать decoder сначала для session/config/time.
3. Для каждого события проверять:
   - минимальную и максимальную длину;
   - диапазоны чисел;
   - границы UTF-8 полей;
   - обязательный terminator/checksum, если он есть в данном типе.
4. Неизвестные команды возвращать как `UNKNOWN`, сохраняя type/length для
   диагностики.

Критерий готовности:

- decoder не хранит указатели во временный RX buffer;
- все fixtures дают ожидаемые типы и значения;
- truncated и oversized corpus проходит без crash и выхода за границы.

### Этап 3 — жизненный цикл соединения и времени

Работы:

1. Описать состояния `OFF`, `ADVERTISING`, `CONNECTED`, `SUBSCRIBED`,
   `SYNCING`, `READY`, `STALE`.
2. Отправлять sync request только после подписки на TX.
3. Повторять запрос после reconnect и по ограниченному timeout/backoff.
4. Применять полученные дату, время и формат 12/24 часа к `watch_clock`.
5. Хранить время последней успешной синхронизации.
6. Передавать Chronos уровень и признак зарядки батареи часов, когда появится
   реальный battery driver.

Критерий готовности:

- время на экране совпадает с телефоном после connect;
- reconnect не создаёт бесконечный поток sync requests;
- отключение телефона не останавливает локальные часы;
- UI различает online и stale без ложного `offline` сразу после краткого
  разрыва.

### Этап 4 — уведомления и звонки

Работы:

1. Ограниченная очередь последних восьми уведомлений.
2. Поля:
   - source/app;
   - timestamp;
   - title;
   - message;
   - semantic icon/category.
3. Безопасное UTF-8 сокращение по границе code point.
4. Dedup по устойчивому ключу из доступных полей.
5. Интеграция с журналом и event precedence:
   - обычное уведомление — неблокирующее;
   - входящий звонок — blocking overlay;
   - завершение звонка удаляет overlay.
6. Очистка локальной очереди без команды, которая может удалить данные на
   телефоне, пока её смысл не подтверждён.

Критерий готовности:

- русские и латинские уведомления не повреждают разметку;
- длинное сообщение не переполняет буфер и экран;
- входящий звонок прерывает обычный экран;
- после завершения звонка восстанавливается прежний контекст.

### Этап 5 — батарея телефона, погода и настройки

Работы:

1. Телефон:
   - battery percent;
   - charging state;
   - timestamp обновления.
2. Погода:
   - текущая температура и icon category;
   - high/low;
   - город;
   - время обновления;
   - затем прогноз до семи дней и 24 почасовых точек.
3. Настройки:
   - quiet hours;
   - water/sedentary reminders;
   - язык и 12/24-hour mode только там, где их семантика подтверждена.
4. Для всех сетевых данных реализовать `fresh/stale/unavailable`.

Критерий готовности:

- главный экран получает реальные погоду и батарею телефона;
- старые данные явно помечаются;
- отсутствие части полей не уничтожает последний валидный snapshot.

### Этап 6 — команды часов → телефон

Работы:

1. Реализовать очередь TX команд и обработку `NRF_ERROR_RESOURCES`.
2. Поддержать:
   - play/pause;
   - next/previous;
   - volume up/down/mute;
   - find phone;
   - camera shutter после отдельного подтверждения в UI.
3. Повтор команды разрешать только там, где операция идемпотентна.
4. Для camera/find phone использовать явное действие пользователя.

Критерий готовности:

- команды работают с реальным телефоном;
- повторное нажатие не оставляет зависшее состояние;
- команда не отправляется после disconnect;
- UI показывает подтверждённый результат или timeout, а не предполагаемый
  успех.

### Этап 7 — навигация

Работы:

1. Поддержать:
   - active/finished;
   - distance;
   - duration и ETA;
   - title/directions;
   - speed;
   - иконку 48×48 1bpp и её CRC.
2. Передавать иконку напрямую в общий asset/bitmap слой.
3. Создать экран ближайшего манёвра в обеих шкурках.
4. Новому манёвру дать приоритет важного, но не blocking события.
5. Не перерисовывать icon, если CRC не изменился.

Критерий готовности:

- смена манёвра появляется без ручного перехода;
- текст безопасно сокращается на круглом экране;
- повтор той же иконки не вызывает лишнюю передачу/перерисовку;
- остановка навигации возвращает предыдущий экран.

### Этап 8 — будильники и дополнительные функции

После стабилизации основных функций:

- до восьми будильников;
- water/sedentary reminders;
- camera remote;
- несколько избранных контактов и SOS;
- ограниченный набор QR-кодов.

Полный список контактов и watchface transfer не являются целями первого
релиза.

### Этап 9 — безопасность, питание и долговременная работа

Работы:

1. Добавить pairing/bonding и модель единственного владельца.
2. Запретить выдачу уведомлений и приём управляющих команд от неизвестного
   телефона.
3. Реализовать удаление владельца через локально подтверждённое действие.
4. Перейти с 20 ms bring-up advertising на адаптивный интервал.
5. Использовать sleep между событиями SoftDevice.
6. Проверить reconnect, radio current и работу в течение 24–72 часов.
7. Добавить protocol version/capability guards для изменений Chronos app.

Критерий готовности:

- чужой телефон не читает уведомления и не управляет устройствами;
- после power cycle часы узнают владельца и восстанавливают соединение;
- потеря телефона не приводит к активному бесконечному advertising;
- длительный тест не показывает утечек состояния или роста ошибок.

## 6. Ограничения памяти

Начальные бюджеты:

| Объект | Бюджет |
| --- | ---: |
| RX frame assembler | 512 байт |
| TX command queue | до 4 × 32 байта |
| Notifications | до 8 записей, суммарно до 4 КиБ |
| Weather daily | до 7 записей |
| Weather hourly | до 24 записей |
| Navigation icon | 288 байт |
| Вся Chronos model | целевой максимум 12 КиБ RAM |

Все пределы должны проверяться compile-time assertions и host tests. Большие
строки сокращаются при декодировании; heap не используется.

## 7. Проверки

### Host

- fixture tests для каждого типа;
- все варианты BLE fragmentation;
- malformed/truncated/oversized corpus;
- UTF-8 boundary cases;
- duplicate и out-of-order события;
- model snapshot tests;
- сборка с ASan/UBSan, если host target это позволяет.

### На часах

- Windows Bleak harness для discovery/RX/TX;
- реальный Chronos на телефоне;
- disconnect/reconnect и power cycle;
- телефон вне зоны действия;
- поток из 100 уведомлений;
- длинные русские строки и emoji;
- смена погоды/навигации во время работы GUI;
- измерение RAM, stack, frame time и тока.

## 8. Порядок поставки

### MVP transport

Этапы 0–3: framing, decoder, session и реальное время.

### Companion v1

Этапы 4–6: уведомления, звонки, погода, батарея и управление телефоном.

### Companion v2

Этап 7: навигация.

### Daily-use gate

Этап 9: bonding, owner recovery, power и длительные тесты. До прохождения
этого gate текущий открытый NUS считается лабораторным режимом.

## 9. Ближайшая задача

Начать с Этапа 0: сохранить обезличенный полный RX trace начальной сессии
Chronos и превратить уже полученные пакеты в первые host fixtures. После этого
реализовать `chronos_frame` независимо от SoftDevice и GUI.

# Экспериментальные часы на ProMicro-nRF52840

Статус: концепция и аппаратный bring-up  
Дата: 2026-07-23

## 1. Назначение

Проект исследует персональные наручные часы на nRF52840 как универсальный
локальный терминал пользователя. Часы должны:

- взаимодействовать с телефоном;
- получать данные, события и доступные действия из экосистемы ТехноСенс;
- взаимодействовать с персональным обнаружителем;
- подключать новые классы устройств без добавления отдельного экрана в
  firmware для каждого устройства;
- оставаться пригодными как самостоятельная экспериментальная платформа для
  датчиков, уведомлений, журналов и пользовательских приложений.

Это не только циферблат и не уменьшенная копия мобильного приложения. Часы —
ограниченный по ресурсам renderer, input-устройство и клиент жизненного цикла
событий/команд.

## 2. Продуктовая идея

Основной экран показывает время, локальное состояние часов и текущий контекст.
Контекстом может быть телефон, объект ТехноСенс, обнаружитель или другое
подключённое устройство. Пользователь должен быстро:

- увидеть наиболее важное подтверждённое значение;
- различить нормальное, устаревшее, ошибочное и offline-состояние;
- получить обычное, важное или блокирующее событие;
- открыть краткую сводку и список параметров устройства;
- выполнить безопасное действие с понятным состоянием доставки и
  подтверждения;
- создать запрос на критическое действие, не выдавая его за исполненную
  команду.

Новые источники должны подключаться через семантические descriptor-ы,
снимки состояния, события и capabilities, а не через загружаемый код или
пиксельную разметку.

## 3. Архитектурная модель интерфейса

Интерфейс следует модели Universal UI v0.1:

```text
domain semantics + runtime state
              │
              ▼
     normalized UI View Model
              │
              ▼
  bounded layout + Display Profile + Skin
              │
              ▼
       display list / draw calls
              │
              ▼
            NOG_C
              │
              ▼
      display driver / framebuffer
```

Слои имеют разные источники истины:

1. Domain semantics — identity, паспорта, channel/capability/event schemas.
2. Runtime state — confirmed values, revision, timestamp, quality, online,
   events и состояния команд.
3. UI View Model — транспортно-независимые экраны, компоненты, bindings и
   actions без абсолютных координат.
4. Layout policy — ограниченные шаблоны и детерминированные fallback-правила
   под Display Profile.
5. Skin — шрифты, интервалы, линии, иконки и визуальные варианты без изменения
   semantics и safety policy.

Телефон, BLE, будущий LoRa-адаптер и протокол обнаружителя не должны проникать
в layout или графическое ядро.

## 4. Роль независимых проектов

### NOG_C

Независимый графический движок общего назначения на C11. Он отвечает за:

- поверхности и pixel formats;
- примитивы, bitmap и текст;
- clipping и viewport;
- streaming/backend API;
- dirty regions;
- окна, элементы и восстановление повреждённых областей.

NOG_C не знает о ТехноСенс, телефоне, обнаружителе, View Model, risk classes,
командах и экранах часов. Изменения, полезные только часам, сначала должны
формулироваться как общий графический контракт и проверяться host-тестами
самого NOG_C.

### TsehoSense Universal UI

Отдельный независимый проект интерфейсного слоя. Он должен владеть:

- JSON Schema и authoring-моделью;
- normalized UI View Model;
- Display Profiles и skins;
- фиксированными template families;
- reference compiler/renderer и golden scenarios;
- форматом compiled UI package;
- C parser/model/layout/display-list;
- input semantics;
- event surface precedence;
- command lifecycle и safety invariants;
- adapters к конкретному drawing backend, включая NOG_C.

UI-проект не должен зависеть от firmware часов, конкретного дисплея или
Theia. Интеграция с ЦехоЛаб, часами и другими устройствами выполняется через
адаптеры.

### Firmware часов

Проект часов владеет:

- startup, clock, power и board support;
- драйверами дисплея, ввода, батареи и периферии;
- BLE и другими transport adapters;
- локальным registry/cache;
- загрузкой UI package;
- интеграцией Universal UI с NOG_C;
- хранением, журналом и bounded retention;
- режимами сна и восстановлением;
- product policy конкретных часов.

## 5. UI-контракт часов

Первая целевая конфигурация — профиль класса `watch`, уточняемый после выбора
экрана. Спецификация уже предусматривает квадратный и круглый 256×256,
`mono1`, safe area, минимальный текст, touch/back input и ограниченные бюджеты.
Фактический Display Profile нельзя фиксировать до идентификации дисплея,
контроллера, формы, pixel format и органов ввода.

Первая версия поддерживает ограниченные template families:

- `home-context`;
- `device-list`;
- `device-overview`;
- `parameter-list`;
- `control-list`;
- `metric-detail`;
- `event-journal`;
- `event-detail`;
- `command-status`;
- `critical-request`.

При нехватке площади renderer убирает вторичные аннотации, заменяет сложное
представление числом, оставляет primary metrics, переносит прочее в список и
использует compact labels. Основной текст не уменьшается ниже минимума профиля.

## 6. Безопасность и достоверность

Обязательные инварианты:

- risk class можно повысить, но нельзя понизить downstream-слоем;
- `critical` на часах означает только создание запроса;
- `approved` не означает `executing` или `completed`;
- blocking event имеет приоритет над любым текущим экраном и статусом команды;
- desired/draft value не является confirmed value;
- команды используют TTL, idempotency key и precondition revision;
- deferred execution по умолчанию запрещено;
- skin не изменяет semantics, источник, единицу, quality или safety policy;
- device-supplied executable code и general-purpose bytecode запрещены;
- несовместимый или повреждённый UI package переводит часы в встроенный
  read-only fallback.

Эти правила применяются и к обнаружителю, и к телефону, и к ТехноСенс.

## 7. Ограничения embedded-реализации

- C11, без обязательного C++;
- отсутствие `malloc` в steady state;
- fixed-size pools и bounded tables;
- нерекурсивный layout;
- integer/fixed-point geometry;
- проверяемый binary package с CRC;
- частичная перерисовка;
- детерминированный fallback;
- host-тесты parser/layout до запуска на nRF52840;
- единые golden scenarios для reference и embedded renderer.

NOG_C используется как drawing backend, но не заменяет UI package parser,
View Model, layout policy или lifecycle событий и команд.

## 8. Первая сквозная демонстрация

Минимально полезный вертикальный срез:

1. часы загружают встроенный тестовый UI package;
2. показывают `home-context`;
3. получают по BLE от телефона снимок одного источника;
4. показывают `device-overview` и два параметра с quality/freshness;
5. показывают ordinary и blocking event с правильным приоритетом;
6. проводят guarded action через hold и отображают полный lifecycle;
7. создают critical request без возможности локального execution;
8. тот же View Model и сценарий воспроизводятся reference renderer-ом на ПК.

После этого источник данных заменяется или дополняется реальным обнаружителем
и шлюзом ТехноСенс без изменения графического движка и template semantics.

## 9. Что пока не определено

- точная ревизия и распиновка ProMicro-nRF52840;
- дисплей, его контроллер, разрешение, форма и pixel format;
- touch/buttons/crown;
- схема питания, аккумулятор, зарядка и измерение батареи;
- набор датчиков, вибромотор и звуковой сигнал;
- RTOS/SDK и модель обновления firmware;
- BLE services и роль phone companion;
- физический и транспортный интерфейс обнаружителя;
- формат первого binary UI package;
- доверие, подпись и обновление UI/skin packages;
- границы автономной работы без телефона/шлюза.

Эти решения требуют отдельных измерений и не должны неявно закрепляться в
графическом или UI-репозитории.

## 10. Критерий успеха экспериментальной платформы

Проект считается состоявшимся, когда одна прошивка часов:

- отображает разные устройства из семантических контрактов;
- сохраняет одинаковый смысл с reference UI;
- безопасно обрабатывает события и команды;
- работает в заданных RAM/Flash/power budgets;
- позволяет независимо обновлять NOG_C, Universal UI и firmware;
- добавляет новый источник без написания device-specific C screen.
